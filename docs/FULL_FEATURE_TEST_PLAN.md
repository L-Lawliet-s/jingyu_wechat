# 小鲸鱼新版完整测试与验收方案

日期：2026-10-27。适用源码基线：`30997407b3093d67b27fe6f90bc16349d0879ea6`。本文件是待执行方案，不是全部功能已通过的报告。

## 1. 测试范围与已知边界

覆盖本轮新增的会聊天的小助手、不同角色卡下的共享记忆、B站资料与播放器、外卖页面操作、自动语音环境、小伊声音、微信语音/视频来电接听，并回归余额、提醒、普通聊天、表情包、连接与配置保存。

当前产品边界必须作为验收依据：

- 微信只接听指定联系人，不主动拨号。视频接听的音频和通话状态需要验收；“小鲸鱼画面区”只是占位，尚未向微信传送立绘或虚拟形象。
- 语音是识别 → 模型回答 → 合成的轮流听说流程，不能按支持随时打断的全双工电话验收。
- 通话可读取该联系人的角色和已允许的文字记忆；语音识别内容尚未自动存入跨聊天长期记忆。
- B站可读取资料、可用字幕、评论和楼中楼并操作播放器；未实现视频画面识别，不能把标题、评论或片段字幕当作看完了整段视频。
- 外卖范围为打开平台、选店选餐、加购和费用核对。登录、验证码、收货信息、订单提交和付款由用户手动完成。淘宝适配入口为淘宝闪购网页，不代表支持淘宝所有购物业务。
- 拍一拍、原生微信语音气泡、自动视频形象传送不能列作本次已完成项。未来加入后另立用例；不能用文字回复代替并标为通过。
- 本次测试文档交付不执行真实消息发送、付费模型对话、下单或电话测试。

## 3. 测试准备

### 3.1 软件与账号

1. 使用 `D:\code\jingyu_wechat\WeChatAgent.exe`，确认加载上述基线或包含它的后续提交。
2. 保存设置后，从托盘完整退出并重开 DSH；只启用当前源码目录的 `packages\dsh-social-bridge-plugin`。保留项目专用微信 4.1.10.27。
3. 小号为被接管账号。测试阶段先只允许主人大号 O，O 为管理员并选择“会聊天的小助手”。不要为测试直接允许所有联系人。
4. 多联系人测试另准备 A、B 两个本人控制或已同意测试的账号，备注唯一。需要时才逐一加入允许范围，A/B 默认不是管理员。没有 A/B 时，对应用例记“阻塞”，不得让真实朋友代替而不说明。
5. 群聊回归使用专用测试群 G；没有群则记录“未执行”，不向日常群发送测试内容。
6. 连接自己的 DeepSeek Key 与可用模型；记录模型名，勿把真实 Key、Cookie、读取令牌和聊天原文贴进公开日志。
7. 使用耳机做语音测试；来电测试前完成虚拟音频驱动安装及重启。安装和设备对应步骤见 [接听配置指南](COMPANION_PLATFORMS_CALLS.md)。
8. 本方案不要求用户手填 Python、模型目录或音频依赖；一键准备失败本身就是应记录的缺陷。

### 3.3 数据与成本

- 开始前在本机留一份配置备份；数据库若要备份，先正常停止相关服务并采用一致性备份，不在写入时随意复制单个数据库文件。备份不得提交 Git。
- 先做离线和页面测试，再做真实文字，最后接电话。故障注入优先使用模拟测试，不去破坏正在使用的 Key、Python 或数据库。
- 第一次实测建议只发约 15–25 条文字、做 2 次不超过 1 分钟的通话。多联系人和长时间测试另批进行。
- 可先设人工停止线，例如本轮最多 30 次模型请求或 1 元预算；这是人工测试约束，不是软件已经具备的总额硬限额。记录前后余额和返回的 token 用量，不能用缓存余额的短时不变证明零费用。
- 关闭临时提醒，清空测试餐品购物车；登录、付款或提交真实订单不属于本方案。

## 4. 执行方式与通过标准

优先级：P0 为连接、权限、记忆隔离、禁止自动付款、接通核验和停止音频；P1 为核心功能；P2 为体验与长期观察。P0 不通过即停止相关模块验收，先保存证据。

本方案共 107 个基础用例；外卖 F01–F07 在美团和淘宝闪购各执行一次，合计 114 条执行记录。多人、多角色的步骤仍需按用例中的全部方向完成，不能只测试其中一个方向。

每项记录：`待测 / 通过 / 失败 / 阻塞 / 不适用`。没有驱动、账号、平台登录或测试环境时用“阻塞”；不能写“通过”。“不适用”必须说明原因。

建议执行顺序：S 启动 → C 聊天任务 → M 记忆 → Q 余额 → B 站 → F 外卖 → V 本地语音 → T 来电 → R 稳定性 → L 旧功能。通话前必须先通过 V01–V06 及 T01–T03。

推荐体验观察线，而非软件时延承诺：普通短消息超过 60 秒无可见结果即开始排查；电话中一句话说完超过 30 秒仍无回答即记录识别、模型、合成各阶段状态。首次加载与平台验证码单独记时，不混入平均耗时。

### T. 微信语音、视频来电接听

双向音频前置：微信扬声器 → VAIO Input；鲸鱼录音 → VAIO Output/B1；鲸鱼播放 → AUX Input；微信麦克风 → AUX Output/B2。Banana 的 VAIO 条只送 B1、AUX 条只送 B2；需要监听对方时 VAIO 可额外送 A1。先核对设备，不能只凭名称勾选“已接通”。

| T04 / P0 | 开启 O 来电接听，先不打电话，观察一分钟。 | 显示等待；不主动拨号、不采集麦克风、不产生对话模型请求。 |
| T05 / P0 | O 向小号发起语音来电，观察真实微信计时和管理页面状态。 | 核对人物后接听；明确接通证据出现前 AI 不工作；接通后才进入音频。 |

额外核对：语音里新说一句唯一虚构标记，挂断后从其他聊天询问。当前版本不保证把语音新事实自动变成长期共享记忆；应记录为当前能力边界，不能把“读取既有文字记忆成功”写成“通话新事实已长期存储”。

# 仅影响当前 PowerShell 进程；确保 Electron 以桌面运行时启动。

普通桌面构建单独执行 `npm.cmd run desktop:build`。完整 NSIS 安装器构建和安装/卸载仍是独立验收项，不用普通构建成功替代。

## 7. 最短实测路线

想先确认“这次升级能不能用”，先做以下流程，再补全其余用例：

1. S01、S03：当前插件启动，新区域全部可见。
2. C01、C03、C04：问候 → 真实 B站评论任务 → 问候，确认任务与聊天都回应。
3. M01、M02、M03、M04、M06、M11：用虚构事实验收自动记忆、主人通读、联系人隔离、私密和不同人设。缺 A/B 时保留阻塞。
4. Q01–Q03：页面与两种自然问法的余额一致。
5. B04、B06、B08、B09：字幕、评论、楼中楼、实际播放器。
6. F01–F05：每个平台各做一次选餐、单份加购、费用核对、不提交订单，随后清购物车。
7. V01、V04、V06 → T01–T10、T13：先试听与本地两轮，再双通道语音来电，最后视频来电。
8. R04、L01：重开后再做一次普通聊天，确认配置、记忆、设备与角色仍正常。

这条路线是首轮验收，不是完整验收；未执行的权限、异常和稳定性项仍保留待测。

## 8. 故障定位顺序

| 表现 | 按顺序检查 | 不应采取的替代结论 |
| --- | --- | --- |
| 小助手不回话 | 消息是否接收 → 允许私聊/真实身份 → DSH 是否完整重开且当前插件根目录正确 → 当前模式/任务分流 → 模型错误 → 发送回执 | 不能只确认微信登录便说整条链路正常 |
| 能聊但不能执行 | O 是否为管理员 → 小助手模式 → 工具授权/审批 → 桌面平台窗口 → 操作结果 | 不给普通联系人加管理员来绕过故障 |
| 不记得论文 | 当前项目是否收到原话 → 自动记忆/分享开关 → 来源与时间 → 私密/移出状态 → 当前账号与角色聊天档案 | 不能把角色卡里手工写入事实当成自动记忆通过 |
| 记忆说串了 | 区分用户原话/AI 回复/引用 → 检查来源人物及权限 → 记录独特标记 → 停止跨人验收并保存最小复现 | 不继续向其他联系人试探真实隐私 |
| 余额不对 | Key 属于哪个 API 账户 → 更新时间/缓存 → 是否查询失败 → 自然问法是否进入可查余额通道 | 查询失败不等于余额为零 |
| B站说看完但无依据 | 查工具是否取得字幕/评论/仅标题 → 检查实际 BV 与当前窗口 | 标题摘要或打开窗口不等于看完画面 |
| 外卖只开网页 | 是否登录/地址可用 → 当前页面控件是否可读 → 搜索/选规格 → 实际购物车 | 未加购不能记“外卖功能通过” |
| 能接听但没声音 | 确认计时 → VAIO/B1 是否收到对方 → 鲸鱼录音设备/识别 → 模型状态 → 合成 → AUX/B2 → 微信麦克风 | 本机试听成功不等于对方收到 AI 声音 |
| 自己不停说话 | VAIO/AUX 是否串送到同一总线 → 实体麦克风是否混入 B1/B2 → 是否识别了自身合成声音 | 先停止音频，不能放任自动循环 |
| 视频没有小鲸鱼画面 | 检查是否仅占位；当前没有虚拟形象输出链路 | 占位区显示正常不等于视频形象已传送 |
| 操作结果未知 | 直接查看微信/购物车 → 保存请求状态 → 人工确认后恢复 | 不靠重复点击、重复加购或重打电话碰运气 |

## 9. 记录表与交付判定

每次执行可复制如下记录，不填写真实密钥和无关聊天内容：

```text
测试批次：
测试时间（北京时间）：
源码提交 / 微信版本 / DSH 版本：
模型名 / 角色卡别名 / 测试账号别名：
用例编号（外卖请加平台名）：
前置条件：
输入与操作：
实际结果：
预期结果：
状态：通过 / 失败 / 阻塞 / 不适用
证据：脱敏截图、时间、错误码、最小必要日志
复现次数 / 尝试次数：
模型请求数 / token / 前后余额时间：
恢复方式 / 关联问题：
```

判定规则：

1. 所有适用 P0 必须通过；任何越权、记忆串线、自动付款、错接联系人或挂断后仍持续采音都应阻止相关模块交付。
2. 核心 P1 真实链路需要通过：小助手既能聊又能做任务；不同人设记忆符合权限；B站实际读取/播放；两家外卖分别实际加购与核对；语音和视频来电实际接通并双向音频正常。
3. 可以单独验收已通过的模块，但报告必须列出阻塞项。例如缺驱动时写“文字与 B站已验收，通话阻塞”，不能写“新版全功能通过”。
4. 平台登录限制、控件不可读、接口变化是实际兼容结果，需要记录平台、时间、页面与错误，不用“网络问题”概括所有失败。
5. P2 的体验问题可记录后续处理；凡影响核心流程或权限则提升优先级。
6. 完整安装包未构建/未实测时单列；主动拨号、原生语音气泡、视频形象和通话新事实长期入库仍按第 1 节边界说明。

建议形成一页最终结果：`模块 → 通过数 / 失败数 / 阻塞数 → 关键证据 → 剩余问题`，并在修复后重跑失败项、受影响的相邻用例与相应自动回归。
